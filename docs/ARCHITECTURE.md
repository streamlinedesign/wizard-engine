# Architecture

Three layers, each only talking to the one below it.

```
game/      the wizard, the hub, items, spells, grimoire, events     (what the game is)
engine/    loop, scenes, canvas + camera, input actions, sprites, tiles (what we own)
ebiten     window, keyboard/mouse/gamepad, GPU drawing, audio          (what we rent)
```

## Why this split

The game needs things no off-the-shelf engine gives you for free: items that
become spells once scrolled into a grimoire, real-time events like moon
phases, blueprints that fill up over days, and eventually a server that runs
the same simulation for several wizards. All of that is data and rules, not
rendering. So the "engine" we write is mostly those systems; Ebitengine is
kept to the parts that are the same in every 2D game.

## engine/

- `engine.go`: `Game` runs a fixed 60 ticks/second `Update` and a `Draw`
  into the virtual canvas. One `Scene` is active at a time; scenes receive a
  `Context` (input, camera, timing) and can swap to another scene.
- `render/`: `Viewport` is the 320x180 canvas, integer-scaled to the window
  with letterboxing. `Camera` follows a target smoothly, clamps to the map,
  and snaps its offset to whole pixels so nothing shimmers.
- `input/`: physical keys map to named `Action`s. Game code asks "is Cast
  pressed", never "is Space pressed". Rebinding, gamepads, and replayed or
  networked input all plug in here.
- `sprite/`: parses Aseprite's JSON export (array or hash form, trimmed or
  not) into `Sheet`s, and `Animator` plays tags with per-frame durations and
  forward/reverse/pingpong direction. `Sprite.Draw` is the only part that
  touches Ebitengine.
- `tilemap/`: fixed-size tiles in layers over one tileset, with a solid flag
  per tile id, AABB collision against solid cells, and culled drawing.

## game/

- `player/`: the controlled wizard. Positioned by the feet, slides along
  walls, picks `idle_*`/`walk_*` animations from facing.
- `scenes/`: `Sandbox` is the step-1 clearing. The hub comes next.

## assets/

Everything under `assets/` is embedded with `go:embed`, so a build is one
file. `assets.Image` and `assets.Sprite` load and cache. The placeholder art
is generated by `tools/mkplaceholders`; real Aseprite exports replace the
files in place (see `ASEPRITE.md`).

## Conventions

- World units are pixels. Tiles are 16x16. Characters are 16x32 cells with
  the feet on the bottom row.
- Simulation is fixed-step (`ctx.DT` is always 1/60 s). Rendering is
  decoupled, so a slow machine drops frames, not game time. This is also
  what makes a future authoritative server possible: the same `Update` runs
  there.
- Floats for positions, whole pixels at draw time.

## Known gaps (on purpose, for now)

- No depth sorting yet: the wizard draws over tree tops instead of behind
  them. Comes with the hub, where it matters.
- No audio, no gamepad bindings, no map editor import. Maps are built in code
  until the hub needs more than that.
